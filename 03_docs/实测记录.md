## 2026-10-20 深夜追加 · USB 打不开的根因（已定位）

**现象**：C 板 USB 能枚举（`USB 串行设备 (COM5)`，PnP 状态 OK），但打开永远报
`Cannot configure port, OSError 22 参数错误`；换线、换口、拔 24V、关终端都无效。

**定位过程**：烧了一个跳过 IMU SPI 读的最小固件（`DBG_MINIMAL 1`）→ **串口立刻正常**。
把 IMU 加回来 → 立刻复现。→ **根因是 IMU 的 SPI 读**。

**为什么缩短超时（100ms→1ms）也没用**：
`HAL_SPI_TransmitReceive(..., Timeout)` 内部用 `HAL_GetTick()` 判超时。
但这段代码跑在 **TIM10 的 1ms 中断**里，而 SysTick 优先级低于它 → **tick 不再递增**
→ `(HAL_GetTick() - Tickstart) > Timeout` 永远不成立 → **死循环**（超时机制整体失效）。
结果 1ms 中断回不来，USB 控制传输彻底没机会响应 → 设备在、口打不开。

**临时办法**：`DBG_MINIMAL 1` —— 不读 IMU，其余（CAN/电机/遥控/打印）全部正常。

**待办**：
1. SPI 读改成**计数器超时**（不依赖 HAL_GetTick），或把 SysTick 优先级提到 TIM10 之上
2. IMU 本身要单独特查：读一次 chip id（0x1E / 0x0F）就能判断 BMI088 是否还活着
3. C 板 24V IN 当时没接（`vbat=4.10`），但电调有电（`ang=4.35` 有数）→ 说明 24V 只接到了电调侧

## 2026-10-20 深夜 · 遥控器打通（M1 达成）

**关键认知**：之前接收机不亮，**是因为当时板上只有 USB 供电**（`vbat=4.10`），DBUS 的 5V 来自
24V 降压（VCC_5V_M）。**接上 24V 后接收机立刻亮灯** → 不是线的问题、也不是口的问题。

**对码后实测**（DBG_MINIMAL 模式下）：

```
sL=158  sR=97  col=-0.01     ← DBUS 帧正常到达！
```

- `sL=158` = SB 在下档（DOWN_POS）
- `sR=97`  = SC 在上档（UP_POS）
- `col=-0.01` = 右摇杆在中位

**档位枚举**：UP=97 / MID=0 / DOWN=158；**SC 拨到下档（158）= 急停**。

**教训汇总（今晚 5 条）**：
1. USB 能枚举但打不开 → 先怀疑固件里有阻塞调用（本次是 SPI 读 IMU），不是线/口/电源
2. `HAL_*_Transmit` 的超时靠 `HAL_GetTick()`，在中断里 tick 不涨 → **超时永不触发 → 死循环**
3. DBUS 的 5V 来自 24V 降压，**只有 USB 时接收机不可能亮**
4. 烧录前先关串口窗口（否则 `ClearCommError`）
5. 没有万用表时，大部分供电问题只能靠"换线/换口/加 24V"这类排除法

## 2026-10-23 晚 · 更正：USB 打不开的真正原因不是 IMU，是"在中断里发 USB"

**背景**：新固件烧进去后，`COM5` 依旧 `Cannot configure port / OSError 22 / Win32 87`（设备枚举正常、PnP 状态 OK）。
先用 SWD 确认 CPU 活着（`g_dbg` 里 `vbat` 在 4.05~4.08 跳动、地址从 0x20002700 变到 0x20002714 = 新固件已生效）。

**隔离实验（决定性）**：只改一个宏，其它代码一字不动 ——

| 固件 | 串口能否打开 |
|---|---|
| `DBG_USB_PRINT 1`（在 1ms 中断里调 `UsbPrintf`/`CDC_Transmit_FS`）| ❌ 打不开（87）|
| `DBG_USB_PRINT 0`（中断里照旧拼字符串，只是不发送）| ✅ **立刻能打开** |

→ **根因是 `CDC_Transmit_FS` 在 1 ms 中断里被调用**，跟 IMU/SPI 无关。
之前"DBG_MINIMAL 后就好了"是巧合（最小模式那次恰好也把打印关掉了/负载变轻）。

**修法（已改，FLASH 47 164 B）**：双缓冲 ——
- 中断里：只 `memcpy` 拼好的行到 `g_tx[]` + 置 `g_txReady`
- 主循环 `UserPollSlow()` 里：关中断拷走并清标志（几微秒）→ **在开中断状态下** `UsbPrintf("%s\r\n", local)`

**修完实测**（USB 供电、未接 24V）：

```
gx=0.00 ... aid=30 gid=15 serr=0 icnt=0 vbat=4.07
m=0.00 tgt=0.00 cur=0 st=1 r1..r4=0.00 t1..t4=0.00 sL=0 sR=0 col=0.00
```

三条结论：
1. **`aid=30(0x1E) / gid=15(0x0F)` → BMI088 芯片是好的**，之前怀疑"硬件坏了"可以排除
2. `icnt=0`：周期读 IMU 仍关闭（`DBG_MINIMAL 1` + `DBG_IMU_IDONLY 1`）→ 打开它的下一步是"把 SPI 读也放主循环"（已经在 `UserPollSlow` 里了，只需 `DBG_MINIMAL 0` 验证）
3. `sL=sR=0`：遥控无信号 —— **因为没接 24V**，DBUS 的 5V 来自 24V 降压，接收机不可能有电（这条 10-20 已经踩过）

**新的铁律（写进学习地图第 18 条）**：**中断里只做实时、只拼数据；USB/UART/SPI 发送一律放主循环。**

### 达成

| 项 | 证据 |

| **左后轮按指令转** | 台架方波 ±20 rpm：`t3=20.00 → r3=1.71/0.20`，`t3=-20.00 → r3=-7.13/-3.85`（**同号 = 跟随**）|

### 漏洞（已修）

接收机未对码时 USART3 上仍有"长度正好 25"的帧，解析结果：

`col = -1.52`（超出 ±1）、`sL = sR = 0`（恰好等于 MID_POS）→ `CtrlHandle` 命中中档分支
→ `UserSetSpeed(-45.73)` → `stopFlag` 被解开（`st=0`）= **没人操作，电机却被使能**。

三道修复：
1. `sbus_to_rc()` 丢弃"整帧全 0"的帧（不更新 `rc_last_tick`）
2. 新增 `rcDataSane()`：任一摇杆值超出 ±1.05 即判遥控无效（这条兜住了本次那条帧）
3. `DBG_BENCH_WHEEL` 台架模式：遥控无效时**自动按 ±20 rpm / 2 s 方波驱动单轮**（便于无遥控验证 ID/接线/方向）
   ⚠️ 上电前轮子必须悬空；接上有效遥控后自动退出该模式

固件：FLASH 47 424 B。教训写进第 19 条：**"收到了帧" ≠ "数据可信"，安全判据要校验数值范围**。

## 2026-10-23 深夜 · 左后轮转起来了（M3 第一步过）

### 通道映射（已确认）

推右摇杆上下时：`col` 与 `q2` 完全同步（`col=0.93 ↔ q2=627`，`col=-0.01 ↔ q2=-8`），

### 遗留：纯 P 静差 45~70%

`t3=29` 时 `r3` 只到 8~17。已按 M2006 的验证结论给底盘 PID 加积分：

⚠️ 注意：积分会让"堵住轮子"时积分饱和，松手瞬间可能冲一下；`componentKiMax` 就是防这个的。

### 第二轮：加积分后振荡（并给出结论）

`ki=0.5 / componentKiMax=6000` 下，目标 `t3=8.18` 时实测：

`r3 = 0.10 → 4.89 → 0.62 → 2.03 → 27.23 → 11.97`（在 0~27 之间乱跳）

原因：积分权限 6000（≈7.3 A）对**空载轮**太大；框架积分不乘 dt，误差 8 rpm 时每秒累积
`0.5×8×1000 = 4000` 单位，1.5 s 就顶到上限 → 冲过头 → 误差变负 → 缓慢回退 → 再冲。

**同时暴露一个测试方法问题**：`col≈0.27` 对应输出轴 8 rpm = 转子 154 rpm，
只有 M3508 空载转速（482 rpm 输出）的 1.6% —— **这是摩擦/齿槽效应主导的病态工况**，
任何 PID 在这里都难稳。判断增益应该在 60~100% 额定转速上做，再回头处理低速。

改：`kp 60→120`、`ki 0.5→0.05`、`componentKiMax 6000→1500`。

## 2026-11-17 · "上电后轮子/机械臂完全没反应"根因：CAN bus-off 锁死（已修）

**现象**：整车 24V 上电后，遥控器在线、摇杆值正常进固件、四轮目标与电流指令都能到 ±12000，
但**四个轮子实测转速始终为 0**；机械臂也不动。

**SWD 诊断证据**（不依赖串口）：
- `CAN1 ESR = 0x01F80017`：**BOFF=1（bus-off）**，TEC=248（发送错误计数满）；
- `CAN1 TSR = 0x82000000`：3 个发送邮箱 **TME=[0,0,0] 全满**（指令全卡着发不出去）；
- `g_rx203/g_rxOther` 停在某个值不再增长（节点已脱离总线）；
- 复位 MCU 后立刻恢复：`ESR=0、BOFF=0、TEC=0`，TSR 的 TME/TXOK 正常翻转，
  RX 计数恢复增长（4 个电调 1kHz 回传），随后推杆轮子就有 rpm 了。

**根因**：`can.c` 里 `AutoBusOff = DISABLE`。C 板先由 ST-Link/USB 供电启动、24V/电调后上
（或 CAN 线临时断开）时，1kHz 的 CAN 指令**没有节点 ACK** → TEC 涨到 248 → **bus-off 永久锁死**，
之后 24V 上电、电调回传正常也永远收不到指令。实测就是这样：板子在 ST-Link 供电下跑了很久
（之前烧录/调试），CAN 早锁死了；用户后来上 24V 但不复位，所以"什么反应都没有"。

**修复**：
- `can.c`：CAN1/CAN2 的 `AutoBusOff` 改为 **ENABLE**（bus-off 后约 1.4ms 自动恢复）。
- 重新编译烧录：FLASH **58,752 B (5.60%)** / RAM 42,584 B (32.49%)，0 error。
- 烧后验证：`ESR=0、BOFF=0、TEC=0`；轮目标 12rpm 时实测出现 7.39/−7.13/0/−7.96 rpm → **轮子转起来了**。

**教训（写进流程）**：
1. 只接 ST-Link/USB 给 C 板上电时，CAN 上没有电调 ACK，旧固件会 bus-off 锁死；
   **新固件能自动恢复**，但更稳妥的顺序是：先上 24V，再插/复位 ST-Link；
2. 以后遇到"遥控正常、目标正常、轮子不转"：先看 CAN1 `ESR/TSR`（BOFF/TEC/TME），
   不要一上来怀疑电机/电调。
## 2026-11-20 · 横移前后漂移：新增交叉补偿（待标定）

- 用户反馈：前后直行、原地转弯都已很好，**只剩纯左右平移时前后偏移较大**。
- 分析：纯横移四轮理论前向分量互相抵消，但麦轮辊子摩擦/装配/重心不对称会形成与 vy
  成正比的**纵向合力** → 车往前/后漂。这不是轮速环问题（四轮目标与回读都正确），
  **轮速里程计也看不见**（属打滑层面的真实位移），只能靠地面真值标定交叉补偿系数。
- 改动（未烧录，K 待标定）：
  - `ChassisTask.h` 新增 ⑦ `CHASSIS_STRAFE_FB_COMP`（默认 0.0）；
  - `ChassisTask.cpp::WheelsSpeedCalc()` 斜坡之后加 `vx -= CHASSIS_STRAFE_FB_COMP * vy;`
    （K>0 = 向左平移时车向前漂；向右平移 vy 变号自动反向补偿）；
  - 标定方法写入文档 §2.5：2 m 纯横移，量前后偏移 Δ，K = Δ / 2.0；
  - 编译 0 error：FLASH **58,768 B (5.60%)** / RAM 42,584 B (32.49%)。
- ⚠️ 若左右平移都往同一侧偏（非左右相反）→ 不是该对称误差，先查机械。
